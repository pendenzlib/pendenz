# Task id type

- Status: accepted
- Date: 2026-10-19

## Context

The id column was a `bigint` identity column and the API used `Long`
everywhere. Many schemas key their rows with UUIDs, and some applications
want to assign the id themselves, for example from a sequence they already
own or to make a task addressable before it is enqueued. Principle 2 says
the schema is the user's; the id type is part of that.

## Decision

The table mapping carries the id type, and the id type flows through the
API as a type parameter: `TaskTable<ID>`, `Pendenz<ID>`, `TaskStore<ID>`,
`TaskRecord<ID>`, `TaskContext<ID>` and `TaskHandler<ID, P>`. Kotlin
infers it from the table; a handler lambda looks the same as before.

Two id types ship in the core, as constants of `IdType`:

| Constant | Column | Who generates when the caller gives no id |
|---|---|---|
| `IdType.BIGINT` | `bigint GENERATED BY DEFAULT AS IDENTITY` | the database |
| `IdType.UUID` | `uuid DEFAULT gen_random_uuid()` | the client, with `UUID.randomUUID()`; the column default serves plain SQL inserts |

`enqueue` takes an optional `id`. When it is given, the row is inserted
under that id and a duplicate fails with the database's constraint error.
When it is absent, the id type decides who generates. `BY DEFAULT` rather
than `ALWAYS` on the identity column is what makes caller-supplied ids
possible on a `bigint` table.

`IdType` is sealed. The in-memory store needs to produce ids without a
database and does so through internal members of the two constants. A
third type, for example text ids that the application always assigns, is
an addition to the core rather than an extension point, until a real need
shows what the extension point must look like.

`TaskTable(name = ...)` without an id type keeps building a `bigint`
table, so the common case changes nothing.

## Rejected alternatives

- **Ids as `String` in the API, converted at the store.** Simple
  signatures, but every caller parses and formats, and a `Long` column
  would accept `"abc"` until the database refuses it.
- **An open `IdType` interface.** Would have to expose JDBC binding and
  id generation for two stores, for a use case nobody has asked for.
- **`TaskContext.id` as `Any`.** Saves a type parameter on handlers and
  loses the type exactly where chaining (v0.3) will need it.

## Consequences

- Every signature that carried a `Long` id carries `ID` now. The change is
  incompatible; nothing is released yet.
- The Java facade will be generic in `ID` as well.
- The DDL for existing `bigint` tables changes from `GENERATED ALWAYS` to
  `GENERATED BY DEFAULT`. Tables created from the old DDL work unchanged as
  long as no caller supplies an id.
- Known difference between the stores (noted on review, 2026-10-19): a
  caller-supplied id that already exists fails with the database's
  `SQLException` on PostgreSQL and with an `IllegalArgumentException` in
  memory. Tests that depend on the exception type are testing the store,
  not the queue.

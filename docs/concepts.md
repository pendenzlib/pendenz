# Concepts

How Pendenz works underneath, one topic per section. The decisions
behind each are in [`adr/`](adr); how to use them is in [`guide.md`](guide.md).

## Tasks and their status

A task is a row. The queue's own columns, status, run time, attempts, lock,
version, are the same for every row; the payload columns belong to the
task type. Its `status` column holds one of ten states; the library
enforces the legal transitions, and so do the generated SQL functions
([Operating with SQL](#operating-with-sql)).

| Status | Who acts next | Meaning |
|---|---|---|
| `PENDING` | Pendenz | Due, waiting to be claimed |
| `SCHEDULED` | Pendenz | Run time in the future |
| `RUNNING` | Pendenz | Claimed, heartbeat running |
| `RETRY_PENDING` | Pendenz | Failed with attempts left, or deferred by its handler; waits for its run time |
| `SUCCEEDED` | nobody | Done |
| `CANCELLED` | nobody | Will never run |
| `FAILED` | a human | Attempts exhausted |
| `REJECTED` | a human | Result refused by validation |
| `QUARANTINED` | a human | Set aside with a reason, by an operator or by its handler |
| `AWAITING_APPROVAL` | a human | Task type requires approval |

## Workers and claiming

Workers poll the table, promote due tasks, claim with `FOR UPDATE SKIP
LOCKED` and run the registered handler. Polling is the default and the
safety net; with the optional trigger from `PostgresDdl.notifyTrigger` and
`PostgresNotify` from `pendenz-postgres-notify` as the worker's `wakeUp`,
a task runs the moment its transaction commits, however long the poll
interval is. Several workers on several JVMs can
share one table. Every write bumps a `version` column; a worker only records
an outcome if the version it claimed is still current, so an operator's SQL
always wins over a running worker.

A running task's lock lasts until `locked_until`: the claim sets it to now
plus the worker's `lockTimeout`, every heartbeat moves it on, so workers with
different timeouts can share a table. Whatever a handler throws, an `Error`
included, is a failed attempt for the retry policy, unless it is one of the
decisions a handler reports ([below](#decisions-a-handler-reports)). When a worker dies with a
task, its lock expires, and the next worker that handles the type records the
lost attempt as failed, with a `LockExpiredException` as the cause. A task
that kills every worker therefore ends `FAILED` after the policy's attempts
instead of running forever.

## Cycles

A cycle runs a task type over a whole dataset. Its tasks come from a
query the application writes, inserted with `INSERT ... SELECT` so the
rows never leave the database, and share the lane `cycle:` plus the
cycle's id:

```kotlin
val cycle = pendenz.startCycle(
    sendInvoice,
    CycleTasks.query("SELECT i.id, c.name FROM invoice i JOIN customer c ON c.id = i.customer_id WHERE i.sent_at IS NULL"),
    description = "October invoices",
)
pendenz.pauseCycle(cycle)    // waiting tasks step aside, running ones finish
pendenz.resumeCycle(cycle)
pendenz.cancelCycle(cycle)
```

For a few tasks known in code, `CycleTasks.of(listOf(...))` takes the
payloads instead of a query and inserts them one by one in the same
transaction. A cycle's tasks can share one resource,
`resource = CycleResource.fixed("mail-server")`, or take it per row from
the query, `CycleTasks.query(sql, resource = "'customer:' || q.customer_id")`.

The cycle lives in a table of its own, generated by
`PostgresDdl.createCycleTable`, and a generated view shows its progress
per task status. Enable cycles with `enableCycles()` on the builder.

### A cycle started by a task

A handler starts a cycle on its context. Nothing is written while the
handler runs; when the task's outcome is recorded as `SUCCEEDED`, the
worker inserts the cycle row and the cycle's tasks in the same
transaction, after the follow-ups, so a crash or a retry can neither
lose the cycle nor start it twice. A recurring task that starts the
weekly invoice run:

```kotlin
Pendenz.create(table) {
    dataSource(dataSource)
    enableCycles()
    register(sendInvoice, SendInvoiceHandler(invoices))
    register(startInvoiceRun) { ctx, run ->
        ctx.startCycle(sendInvoice, CycleTasks.query(UNSENT_INVOICES), description = run.description)
    }
    schedule(
        "weekly-invoices",
        startInvoiceRun,
        StartInvoiceRun("Weekly invoices"),
        Schedule.cron("0 13 * * 1", ZoneId.of("Europe/Berlin")),
    )
}
```

- The query runs when the outcome is recorded, not at the call, and
  sees what is committed then. It runs inside that transaction, which
  holds the task's row meanwhile; other tasks go on.
- The cycle and its tasks inherit the task's creator and correlation
  id; the tasks name the task as their parent and take its priority
  unless `priority` is given. A cycle started by an occurrence of a
  schedule therefore carries `schedule:<name>` as its creator.
- The cycle gets a lane of its own, also when the starting task is
  itself part of a cycle.
- Permissions are not asked, as for follow-ups; the approval rule of
  the cycle's type applies with the inherited creator.
- `startCycle` returns nothing, because the id is generated at the
  insert. A handler that needs the id passes `id`.
- A mistake the call can see fails the attempt with its own message:
  cycles not enabled, a type that is not registered, a query on the
  in-memory store. A query that fails in the database fails the write
  of the outcome: the task stays `RUNNING` until its lock expires,
  which counts as a failed attempt with the error of an expired lock
  for the retry policy; the query's error is in the worker's log.
- Whether runs overlap is the handler's decision: it reads the cycles
  of its type and does not call `startCycle` while one is active.

`Pendenz.startCycle` remains the way to start a cycle from outside a
handler and inside the application's own transaction
([ADR 0047](adr/0047-start-a-cycle-from-a-handler.md)).

## Chaining

A handler that has a next step enqueues it on its context. Nothing is
written until the task's outcome is recorded; then the follow-ups go into
the same transaction, with the task as their parent and the chain's
correlation id, so a crash can neither lose them nor double them:

```kotlin
register(sendInvoice) { ctx, invoice ->
    mail.send(invoice)
    ctx.enqueue(remind, Reminder(invoice.id), runAt = Instant.now().plus(Duration.ofDays(14)))
}
```

## Recurring tasks

A schedule enqueues a fixed payload of a registered type at every fire
time. The queue keeps exactly one occurrence ahead as an ordinary row: it
is `SCHEDULED` until its fire time, then claimed, retried, approved and
retained like any task. When it ends, the worker writes the next one in
the same transaction; a check at worker start, in every maintenance sweep
and in `runPending` starts a series and repairs one an operator broke.

```kotlin
Pendenz.create(table) {
    dataSource(dataSource)
    register(nightlyReport, ReportHandler(reports))
    schedule(
        "nightly-report",
        nightlyReport,
        ReportRequest("all"),
        Schedule.cron("0 3 * * *", ZoneId.of("Europe/Berlin")),
    )
}
```

`Schedule.every`, `Schedule.daily` and `Schedule.cron` with the five
standard fields are built in; anything else implements the one-method
interface. Occurrences never overlap. A failed occurrence waits for a
person while the next one runs on time; after a downtime the overdue
occurrence runs once and the fire times in between are skipped;
cancelling an occurrence skips that run. Every instance may check: the
fire time is in the occurrence's idempotency key, and a lock per schedule
keeps two instances from inserting at once.

`schedules()` reads where every schedule of the queue stands: its newest
occurrence, its newest successful one, and when it runs next, null while
the series is broken. It reads and never inserts
([ADR 0034](adr/0034-schedules-in-spring-and-micrometer.md)).

A schedule enqueues one task. To run a whole dataset at every fire
time, the occurrence's handler
[starts a cycle](#a-cycle-started-by-a-task).

## Results, validation, provenance, preview

A handler may produce a result. It is registered with how to store and
how to validate it; the worker validates before it writes, and a refused
result lands in `REJECTED` for a person, with the result and the reason
in the row. Handlers attach provenance, the code or model version that
produced the result, and a task type may compute a preview of what a
task would do, stored at enqueue for the person who approves it:

```kotlin
val scoreTicket = TaskType.json<Ticket>("score-ticket", preview = { "Score ticket ${it.id}" })
register(scoreTicket, TaskResult.json<Ticket, Score> { _, s -> if (s.value in 0..100) Verdict.accept() else Verdict.reject("out of range") }) { ctx, ticket ->
    ctx.provenance("model", "claude-sonnet-5-5")
    model.score(ticket)
}
```

## Approval and permissions

Some tasks need a second pair of eyes. An approval rule on the task type
holds them as `AWAITING_APPROVAL` until someone who is not their creator
approves or declines. A cycle's tasks are approved in one call; follow-ups
of other types they enqueue wait for their own approval. Who may enqueue,
approve, restart or cancel what is a `Permissions` implementation over the
application's own permission system, checked before anything is written:

```kotlin
val refund = TaskType.json<Refund>("refund", approval = Approval.rule { createdBy, p -> p == null || p.amount > 1000 })

Pendenz.create {
    permissions { actor, action, type -> myAuth.may(actor, action.name.lowercase(), type) }
    register(refund) { _, r -> payments.refund(r) }
}
pendenz.approve(id, actor = "manager")
```

`Action` names every guarded operation: `ENQUEUE`, `APPROVE`, `DECLINE`,
`RESTART`, `COMPLETE`, `QUARANTINE`, `CANCEL`, and for cycles
`START_CYCLE`, `APPROVE_CYCLE`, `PAUSE_CYCLE`, `RESUME_CYCLE` and
`CANCEL_CYCLE`. Without a permission system of its own, an application
lists grants in a `PermissionTable`; anyone not listed, and every
anonymous caller, may do nothing:

```kotlin
permissions(Permissions.table {
    actor("clerk").may(Action.ENQUEUE, "refund")
    actor("manager").may(Action.APPROVE, "refund").may(Action.DECLINE, "refund")
    actor("ops").may(Action.RESTART).may(Action.CANCEL)    // on every type
})
```

The default, `Permissions.ALLOW_ALL`, allows everything. The check
covers the API, the Java facade and the MCP server; SQL is governed by
the database's grants ([ADR 0018](adr/0018-approval-and-permissions.md)).

## Resource limits

A task may name the resource it runs against, and a limit table says how
many tasks of a resource may run at once, across all workers. The claim
skips tasks whose resource is full; an operator changes the limit with
SQL, effective at the next poll:

```kotlin
val sendInvoice = TaskType.columns<SendInvoice>(..., resource = TaskResource.fixed("mail-server", maxRunning = 4))
val notify = TaskType.json<Notify>("notify", resource = TaskResource.fromPayload({ "customer:${it.customerId}" }, "customer:%", 2))
```

Enable it with `enableResourceLimits()` on the builder and
`PostgresDdl.createResourceLimitTable` in your migration.

A limit row names an exact resource or a `LIKE` pattern such as
`customer:%`; when several match, the longest name wins, and a resource
without a matching row is unlimited. A limit a task type declares is
inserted when a worker starts, and only where no row exists, so an
operator's change survives a restart. From code, `setResourceLimit(name, maxRunning)`,
`removeResourceLimit(name)` and `resourceLimits()` do what the SQL does.

A limit of 0 pauses a resource: its tasks stay `PENDING`, running ones
finish. `setResourceLimit("customer:%", 0)` pauses every customer, and
a longer row such as `customer:acme` with a limit above 0 lets that one
through. Unlike a block ([below](#decisions-a-handler-reports)), a pause
has no end time; it lasts until the limit is raised.

## Resource rates

A limit bounds how many tasks run at the same moment, not how many start
per minute. A partner API that allows 100 calls per minute is exceeded by
two tasks in flight whose calls take half a second. A rate row says how
many tasks of a resource may be claimed within any window of a given
length, across all workers
([ADR 0040](adr/0040-rate-limits-per-resource.md)):

```kotlin
val syncCustomer = TaskType.json<SyncCustomer>(
    "sync-customer",
    resource = TaskResource.fromPayload({ "partner:${it.partner}" }, "partner:%", maxStarts = 100, per = Duration.ofMinutes(1)),
)
```

Enable it with `enableResourceRates()` beside `enableResourceLimits()`,
whose claim lock it uses (the limit table may stay empty), and create
the tables with `PostgresDdl.createResourceRateTable` and
`createResourceStartTable`.

- A rate row holds an exact resource or a `LIKE` pattern, a number of
  starts and a window as an `interval`. The longest matching name wins,
  independently of the limit table; a resource may have a limit, a rate,
  both or neither. With a pattern, every resource value gets its own
  rate.
- Every claim of a task whose resource has a rate writes a row into the
  start table: first attempts, retries and the claim after an expired
  lock alike. The poll counts the rows inside each window and leaves a
  resource that used its rate out, as it does with a full one; its tasks
  stay `PENDING` until the window has moved on far enough, and the next
  poll after that claims them.
- The maintenance sweep deletes start rows older than the longest
  window.
- A rate a task type declares is inserted where no row exists, as for
  limits. From code, `setResourceRate(name, maxStarts, per)`,
  `removeResourceRate(name)` and `resourceRates()` do what the SQL does.

A rate keeps a quota; a block ([below](#decisions-a-handler-reports))
reacts when the partner refuses anyway.

## Decisions a handler reports

Some answers are neither a success nor a failure. A handler reports them
by throwing; the worker looks for them in the cause chain, so a client
library deep in the handler may throw them, and records the outcome
without asking the retry policy
([ADR 0035](adr/0035-decisions-a-handler-reports.md)):

| Thrown | Outcome |
|---|---|
| `RetryLaterException(at, reason)` | `RETRY_PENDING` until `at`; the attempt does not count |
| `ResourceUnavailableException(until, reason, resource)` | as above, and no task of the resource is claimed before `until` |
| `HandOverException(reason)` | `QUARANTINED` with the reason, for a person |

```kotlin
register(syncCustomer) { _, sync ->
    val response = partnerApi.push(sync)
    if (response.status == 429) {
        throw ResourceUnavailableException(Instant.now().plus(response.retryAfter), "partner quota used up")
    }
    if (response.status == 422) throw HandOverException("partner refused the record: ${response.body}")
}
```

- A time that is not after now counts as a failed attempt, so that a
  `Retry-After: 0` goes through the retry policy instead of looping.
- The block names the task's own resource unless the exception names
  another. It lives in a table of its own, enabled with
  `enableResourceBlocks()` on the builder and created with
  `PostgresDdl.createResourceBlockTable`. A row holds an exact resource
  or a `LIKE` pattern; any row whose time lies ahead blocks, whatever the
  limits say. A second report never shortens a block.
- The block is written in the transaction that records the outcome. The
  poll reads the active blocks once; tasks of a blocked resource stay
  `PENDING`, running ones go on, and when the time has passed the next
  poll claims them. The maintenance sweep deletes expired rows.
- Without the block table, `ResourceUnavailableException` defers the task
  only and logs a warning once per resource.
- Operators lift a block with `DELETE`, set one with an `INSERT`, or use
  `blockResource`, `unblockResource` and `resourceBlocks` on the queue.
- A deferral drops the handler's follow-ups and keeps a schedule waiting
  for the deferred occurrence; a hand-over lets the next occurrence come.
  The listener hears `onDeferred`, `onHandedOver` and `onResourceBlocked`.

## Fairness and priority

Workers take due tasks fairly. A `lane`, say a tenant or a batch, groups
tasks within a type; each poll visits the lanes in turn, so a batch of ten
thousand and a single task enqueued a second later alternate. `priority`
is a strict tier above that: higher runs first. First come, first served
is still available as `FifoClaim` for teams that need arrival order.

A task type that is cheap to run can set `claimBatchSize`, so a worker
takes several of its tasks from one lane per visit instead of one; lanes
still take turns.

## Replacing parts

Every part the queue uses has a default and an interface (principle 1):

| Part | Default | Set with |
|---|---|---|
| `RetryPolicy` | `ExponentialBackoff()` | the task type |
| `PayloadCodec` | kotlinx-serialization | the task type; Jackson in `pendenz-serialization-jackson` |
| `ClaimStrategy` | `FairClaim()` | `WorkerOptions.claimStrategy` |
| `WakeUp` | `WakeUp.POLLING` | `WorkerOptions.wakeUp`; `PostgresNotify` in `pendenz-postgres-notify` |
| `ConnectionProvider` | with `dataSource(...)`, one connection and transaction per operation | `connectionProvider(...)`; Spring's in `pendenz-spring` |
| `Clock` | `Clock.systemUTC()` | `clock(...)` |
| `Permissions` | `Permissions.ALLOW_ALL` | `permissions(...)` |
| `ErrorDescription` | `Throwable.toString()` | `errorDescription(...)` |
| `TaskInterceptor` | none | `interceptor(...)`, several in order |
| `CallerDefaults` | none: actor and correlation id stay empty when a call leaves them out | `callerDefaults(...)` |
| `TaskListener` | none | `listener(...)`, several; Micrometer's in `pendenz-micrometer` |
| `TaskStore` | `JdbcTaskStore` | `store(...)`; `inMemory()` for tests |
| `SqlDialect` | `PostgresDialect` | `JdbcTaskStore(..., dialect = ...)` |

Interceptors, caller defaults and the error text are described in the
[guide](guide.md#around-every-handler), listeners in
[`metrics.md`](metrics.md).

A **claim strategy** decides which due tasks a poll takes, through
`Claims`: `dueGroups()` lists the `(priority, type, lane)` groups with due
work, `fromGroup` and `oldest` claim from them. The worker does the
claiming, under its lock deadline and the resource limits, so a strategy
can reorder work but cannot break a limit. One that serves a single
lane before all others:

```kotlin
class LaneFirst(private val lane: String) : ClaimStrategy {
    private val fair = FairClaim()

    override fun <ID : Any> claim(claims: Claims<ID>, request: ClaimRequest): List<ClaimedTask<ID>> {
        if (request.limit <= 0) return emptyList()
        val first = mutableListOf<ClaimedTask<ID>>()
        for (group in claims.dueGroups().filter { it.lane == lane }) {
            first += claims.fromGroup(group, request.limit - first.size)
            if (first.size == request.limit) return first
        }
        return first + fair.claim(claims, ClaimRequest(request.batchSizes, request.limit - first.size))
    }
}
```

A **store** is everything the queue does to its rows, as plain
operations inside a transaction the store defines; the in-memory store
and the JDBC store are the two implementations, tested against the same
contract in the repository ([ADR 0006](adr/0006-store-seam-and-in-memory-mode.md)).
With `store(...)`, the builder's `enableCycles()`, `enableResourceLimits()`,
`enableResourceBlocks()` and `enableResourceRates()` are refused; the store brings its own
tables. A **dialect** produces the SQL that `JdbcTaskStore` binds and
runs, for another database than PostgreSQL ([ADR 0008](adr/0008-sql-dialect.md)).
Both interfaces are public so that a second database can be proven
outside the core. Before 1.0 they may still break, as [ADR 0035](adr/0035-decisions-a-handler-reports.md) broke
them; every break is named in the CHANGELOG.

## Operating with SQL

`PostgresOperatorDdl.views` generates three views for operators: failed
tasks grouped by error, running tasks whose heartbeat stopped, and
everything that waits for a human. `PostgresOperatorDdl.functions`
generates `_restart`, `_complete`, `_quarantine` and `_cancel` functions
that take the id and the version the caller saw, apply the legal
transition and return whether the row changed, so a UI or a script never
has to know the rules. [`sql-recipes.md`](sql-recipes.md) shows them, and
the plain SQL behind them, at work.

## Agents

An AI agent uses the queue through MCP. The application names the task
types an agent may use; each becomes a tool that enqueues, beside
`preview_<type>`, `get_task` and `list_tasks`. Every call acts as one
actor, so the approval rule can hold what the agent creates and the
agent can never approve it, and the agent sees only its own tasks:

```kotlin
val mcp = PendenzMcp.create(pendenz, IdType.BIGINT, actor = "ticket-agent") {
    tool(escalateTicket, "Escalates a ticket to second level.", JsonSchema.of<Escalation>())
}
mcp.serveStdio()                         // an agent host starts this application
servletContext.addServlet("mcp", mcp.servlet("/mcp")).addMapping("/mcp")   // or Streamable HTTP
```

More in [`agents.md`](agents.md).

## Stopping a worker

Stopping a worker means cancelling its coroutine. It stops claiming at once,
gives running handlers `shutdownTimeout` (thirty seconds by default) to
finish, then cancels the rest and hands their tasks back as `PENDING` so
another worker picks them up without waiting for the lock timeout. A
handler that ignores the cancellation, say one blocked in a socket read,
is waited for and its outcome recorded, since the work was done; its
heartbeat has stopped, though, so past the lock timeout the next worker
counts the attempt as failed and the late outcome is dropped.
